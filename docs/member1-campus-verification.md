# 成员一：校园身份认证接口预留与验收记录

本次开发及测试仅在开发副本与 `campus_system_dev_test` 完成；用户验收后，按文件清单同步稳定项目。尚未接入学校认证平台，没有真实认证成功数据，不包含身份证、证件照片、支付信息或教务账号密码。

## 已实现的行为

- 个人中心增加“校园身份认证”区域，显示认证服务是否开放、认证状态及说明；未接入时禁用申请，强行调用接口也不能通过认证。
- 学校、学院、学号仍是本人填写的资料，与可信认证记录分离。填写完整资料不会变成“已认证”。
- 普通用户只能申请和查询自己的认证。管理员不能替用户调用申请接口，前端不能指定目标用户、学校快照或认证结论。
- 申请使用数据库中已保存的学校和学号，并要求明确同意资料使用说明。学院、手机号不发送给适配器。
- 修改学校或学号时，在资料保存的同一事务中将原认证失效；改回旧资料也不会恢复原认证。修改昵称、学院、联系方式不影响认证。
- 保存申请历史和平台结果引用，查询响应仅显示脱敏的申请学号，不返回平台凭据引用。
- 已认证结果需要平台凭据和未来的有效期；过期自动显示为已过期，可以重新申请。
- 相同的有效认证或待处理申请不会重复创建。平台超时保留原申请，使用同一请求号重试。

## 接口约定

三个接口均要求普通用户 JWT（`Authorization: Bearer ...`），真实身份仍以服务端当前登录用户为准。

| 方法与路径 | 请求 | 行为 |
| --- | --- | --- |
| GET `/user/profile/campus-verification` | 无 | 查询自己的认证状态及服务可用性，不触发外部核验 |
| POST `/user/profile/campus-verification` | `{"consent":true}` | 保存学校、学号快照与唯一请求号，建立本地待处理申请 |
| POST `/user/profile/campus-verification/refresh` | 无 | 由后端适配器幂等发起/查询平台核验，再更新本地结果 |

成功使用项目统一 `Result` 格式，`data` 包含 `available`、`status`、`message`、`school`、`maskedStudentNumber`、`requestedAt`、`checkedAt`、`expiresAt`。无历史记录时相关申请字段为 null。

状态：`UNVERIFIED` 未申请，`PENDING` 待处理，`VERIFIED` 已通过，`REJECTED` 未通过，`INVALIDATED` 资料变化失效，`EXPIRED` 已过期。平台可用性由 `available` 单独表示，不会把平台未接入伪装为认证成功。

错误：未登录 401、身份不符/账号失效 403、未同意或缺少校园资料 400、状态冲突/平台变化 409、平台响应无效/超时 502、平台未接入 503。客户端传入的 `id`、`status`、`school` 等不参与认证决定。

## 将来接学校平台的方法

实现后端 `CampusVerificationProvider` 并注册为 Spring Bean，替换默认不可用适配器；没有通过修改前端或设置一个开关来“自动认证”的机制。

1. `key()` 返回稳定的平台标识，`available()` 只在凭据、学校范围和平台连接配置齐全时返回 true。
2. `check(Request)` 接收唯一 `requestId`、申请学校和学号。按请求号幂等发起/查询，验证学校范围、学校平台的可信响应及其与该申请的绑定；必须证明申请者拥有该校园身份，不能把“学号存在于学校数据库”视为认证成功。若采用学校 SSO，接入时还需补充学校授权跳转、state/nonce 绑定和授权结果兑换，不能仅凭学校和学号非空就返回通过。
3. 结果仅为 PENDING、VERIFIED 或 REJECTED；终态提供可追溯的平台凭据引用，通过时必须提供有效期。服务端记录检查时间，用户请求不能携带可信结论。
4. 网络调用设置严格连接/读取超时（建议总时限低于 5 秒）并校验 TLS，凭据只放忽略的本机配置或环境变量，不记录完整学号/平台原始响应到日志。查询期间持有当前用户行锁，避免资料修改和结果写入交错；平台调用不宜长期等待。
5. 接入后补充该学校的平台契约测试、异常与重试测试。前端申请后点击“查询认证结果”触发平台处理。

当前没有公开结果回调接口，也没有管理员手动设置通过的接口。确定实际平台的签名、时间戳、请求绑定和防重放规则后再增加专用回调；禁止直接添加匿名的“设置已认证”接口。校园身份认证不等同于法律实名认证。

## 数据库迁移

先备份目标库，再执行 `sql/migrations/20261110_campus_verification.sql`。它只新增 `campus_verification` 表（依赖已有 `base_user` 表），不包含 `USE`、业务数据覆盖或用户密码修改。重复执行不会重复创建表。申请删除随所属账号级联删除。

本次测试库已执行两次，原有 16 张表校验值不变，新表初始 0 行。测试库备份位于忽略的 `.local-backups/campus-verification-migration-*`，不能上传 GitHub。同步稳定环境时，仅执行该结构迁移并保留稳定库原有数据，不复制测试申请或测试账号；稳定项目保留自己的 Git 历史、本机配置和上传文件。

回退应用前先保留认证表与历史数据；不提供自动删表脚本，避免丢失接入后的真实记录。

自动化入口：后端 `mvn -o -B -ntp test`（通过本机环境变量 `CAMPUS_STATS_DB_PASSWORD` 开启独立测试库测试，不要在命令文本中填写密码）；前端 `npm run build`；仓库根目录运行 `node view/tests/campus-verification-browser.cjs` 和 `node view/tests/user-profile-browser.cjs`。浏览器测试要求开发服务 21090/21091 已启动，并使用测试库，结束后自动删除临时账号和生成的测试头像。

实际执行结果及截图：`docs/accessibility-evidence/campus-verification-*-results.json`、`campus-verification-standard.png`、`campus-verification-large.png`。测试证据不包含登录令牌、密码或完整学号。

2026-11-10 实测：后端 209 项全部通过（其中新增校园认证 31 项），前端构建通过，校园认证浏览器 18 项通过，个人中心回归 26 项通过；临时账号及生成的测试头像已清理。原有 16 张表在迁移前后校验值一致。最终后端已加载本次修改，仍仅连接独立测试库。
