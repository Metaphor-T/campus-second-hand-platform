# 订单售后与七天期限

普通售后从买家确认收货完成交易时起计算七天，截止时间保存在订单中。节点和期限统一按北京时间记录，精度为秒。截止时刻起不能再提交普通申请；前端显示入口，后端仍独立检查期限与权限。

未确认收货、处于待收货阶段的订单可以申请售后，不提前计算七天。截止前已经提交的申请继续处理，不因审核时超过七天而失效。缺少完成时间、完成时间异常、超过普通期限或普通申请被驳回的订单，可说明原因申请管理员介入，不能猜测或补写历史时间。

## 处理流程

1. 买家填写申请原因，可上传最多3张JPG/PNG凭证（每张不超过2MB），选择退款并退回商品或仅退款。
2. 普通申请先等待卖家回应。卖家必须填写说明，可同意或拒绝；两个操作都会进入管理员审核，不直接完成退款。
3. 管理员介入申请直接进入管理员审核；尚未回应的卖家仍可补充一次同意或拒绝意见，历史待核对申请也支持补充。管理员填写说明，审核通过或驳回，并确认是否需要退回商品。
4. 无需退回商品的申请审核通过后结束售后，不增加库存。需要退回商品的申请先等待收回；卖家或管理员明确确认实际收到本单退回商品并填写说明后，才处理库存并结束售后。
5. 买家可撤回尚待卖家回应或管理员审核的新申请，原交易状态保留。已审核通过等待退回的申请及历史待核对记录不能直接撤回。

售后单独保存在 `order_after_sale`，包含申请、卖家意见、管理员审核、退回确认、处理者、节点时间和库存处理结果。同一订单只能有一笔处理中申请。交易的原状态在处理期间保持，确认收货等交易操作在售后处理中暂停。

售后状态为：`WAIT_SELLER`、`WAIT_ADMIN`、`WAIT_RETURN`、`APPROVED`、`REJECTED`、`WITHDRAWN`。订单中心的“退款/售后”筛选优先显示前三类处理中记录，计数不重复计算。“已结束”筛选包含取消及售后完成。售后完成后订单结束，界面显示“售后已完成”，不会写成买家主动取消。审核驳回或买家撤回不会取消正常交易。

仪表盘也优先将处理中申请计入退款/售后，不重复计入当前完成订单及其金额、数量和评价覆盖率。申请撤回或审核驳回后，按原交易状态恢复统计；新增趋势仍按订单原创建日期统计。

订单详情时间线展示实际保存的申请、卖家回应、管理员审核和退回确认。业务仅记录模拟退款处理，不执行真实资金转账。

## 库存模式调整

售罄后可以在信息确认窗口选择不限库存并重新提交审核，历史订单不会永久阻止上架。新订单记录下单时的 `stock_mode_snapshot`；后续修改商品不改变旧订单。

- 原有限库存订单取消或确认收到退回商品时，只释放原订单实际扣减的数量，重复操作不会重复增加。
- 当前商品仍为有限库存时，在数量上限允许的情况下增加可售库存；手动下架状态保留。
- 当前商品改为不限库存时，只记录释放/退回数量，不给不限库存的数量字段累加。以后改回有限库存，由卖家重新确认实际可售数量。
- 当前库存模式待确认、商品已不存在、历史扣库不明或数量达到上限时，保存明确的待核对结果，不猜测增加可售数量。售后窗口会显示此结果。
- 仅退款、不退回商品的申请不会恢复库存。

订单的 `stock_released_quantity` 和 `stock_release_disposition` 保留释放数量与处理方式；售后表另外记录实物退回数量和实际增加的可售库存，两者含义不同。

## 已有数据库升级

先备份并停止旧后端，再更新代码和数据库。开发阶段只操作独立库 `campus_system_dev_test`。

1. 一次执行 [升级说明中的完整增量 SQL](project-upgrade-20261111.md#保留原数据库增量升级)，其中已按顺序整合库存和售后两部分。
2. 脚本可重复执行，新增库存模式、售后表及订单的库存模式快照、售后截止时间、释放数量和处理方式四个字段。
3. 只有原来已保存收货时间的订单才据此计算七天期限。库存快照只回填能够从原扣减记录确定的模式；历史不明值保持为空。
4. 旧 `order_status=5` 的订单进入 `LEGACY / WAIT_ADMIN` 队列，保留旧订单状态和原字段。原申请时间、原交易状态不推断；管理员驳回这类申请时须先核对原状态是待收货还是已完成。
5. 启动更新后的后端。旧的直接退款、卖家直接同意退款、管理员直接同意退款接口已停用，统一使用售后窗口，防止绕过新流程。

新建空库只完整执行 [`sql/db.sql`](../sql/db.sql)，已整合库存和售后结构，不需另行执行迁移。不要用完整 SQL 覆盖已有数据库。

开发阶段迁移及测试只在独立测试库进行；稳定项目和稳定数据库仅在用户验收授权后做保留数据的增量同步。本机配置、数据库凭据、上传文件和测试记录不随迁移脚本发布。
