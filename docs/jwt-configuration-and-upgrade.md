# JWT 密钥：本地首次启动与旧部署升级

JWT 密钥只供后端签发和验证登录凭据使用，与数据库密码、用户登录密码无关。普通用户不需要填写。

## 本地开发：首次启动自动配置

项目默认使用 `local` 模式。配置好自己的数据库后即可启动后端，无需手工填写 JWT 密钥。

后端按以下优先级选择密钥：

1. 已有的 `security.jwt.secret` 配置（包含环境变量 `CAMPUS_JWT_SECRET`）：继续使用，不覆盖、不轮换。配置的值无效时会报错，不改用另一份密钥。
2. 没有显式密钥时，读取已有的密钥文件。
3. 只有在单独启用 `local` 模式且文件不存在时，才首次生成 64 字节随机密钥，转成 Base64 保存。后续启动读取同一份文件，正常重启不会因此要求用户重新登录。

Maven/IDEA 从后端模块的编译目录运行时，默认文件位置是 `api/.local-secrets/jwt.key`，由代码所在的模块定位，不根据终端当前目录定位。在项目内运行打包 JAR 也会复用该模块位置；单独复制到其他目录运行的 JAR 使用 JAR 旁的 `.local-secrets/jwt.key`。

启动日志只显示密钥文件位置，不显示密钥内容。文件权限限制为当前运行账号可访问；生成的文件和创建过程的锁文件均由 `.local-secrets/` 规则忽略，不放入 SQL，也不提交 Git。

如果 IDE 使用了不同的编译输出布局，或需要让文件位置独立于代码目录，可配置绝对路径：

```yaml
security:
  jwt:
    key-file: "D:/campus-secrets/dev/jwt.key"
```

也可设置环境变量 `CAMPUS_JWT_KEY_FILE`。相对的自定义路径按启动工作目录解析，跨目录运行时推荐绝对路径。首次自动生成只对 `local` 模式开放。

## 已经配置过密钥的成员

已有的本机 `application-local.yml` 或环境变量配置优先使用，更新代码不会覆盖它。若多处设置了不同值，应整理成一个明确来源；本机文件直接配置的 `security.jwt.secret` 可能覆盖基础配置中对 `CAMPUS_JWT_SECRET` 的引用。

不要为正常更新或重启重新生成密钥。保留原配置或密钥文件，可以避免不必要的登录凭据失效。

## 旧版本将密钥写在源码中的成员如何更新

1. 先备份个人代码修改、数据库连接配置、上传文件和数据库。如果已经有独立密钥，也备份该配置或文件。
2. 因仓库此前清理过 Git 历史，仍持有清理前副本的成员应重新克隆最新 `main` 到新目录；已使用清理后历史的成员可正常更新。不要直接合并旧历史。
3. 将自己的数据库地址、账号和密码迁移到新项目的本机配置，保留原有数据库。不要整份复制旧 `application.yml` 覆盖新版，也不要把源码中的历史共享密钥重新写回代码。
4. 本地课程演示：使用默认 `local` 模式启动。未配置独立密钥时会首次生成并保存，记录日志显示的文件位置。
5. 正式服务器：按下一节提供独立密钥及生产模式，再构建、部署并重启后端。
6. 从旧共享密钥和旧身份凭据升级后，通知用户重新登录，账号和密码继续使用。

JWT 调整不需要修改数据库结构或导入 SQL。若版本跨度较大、缺少其他功能需要的表或字段，应另行核对数据库结构；不要直接向已有库执行完整 `db.sql`。图片文件也需要单独保留。

重新克隆、移动项目或更换服务器时，保留自己的密钥配置；自动生成文件不会随 Git 下载。需要延续同一部署的登录凭据时，应把原密钥文件迁移到明确的持久化位置并配置该路径，不要拿其他成员开发环境的密钥混用。

## 正式服务器：显式配置，禁止自动生成

启动时必须显式启用生产模式，例如环境变量 `SPRING_PROFILES_ACTIVE=prod`。默认 `local` 仅适合本地开发；同时启用 `local,prod` 也不会允许自动生成。

正式环境选择以下一种方式提供密钥：

- 通过部署环境或密钥管理工具设置 `CAMPUS_JWT_SECRET`；不要把真实值写进 Git 或前端环境变量。
- 通过 `CAMPUS_JWT_KEY_FILE` 或 `security.jwt.key-file` 指定已经准备好的持久化密钥文件的绝对路径。生产模式只读取，不创建目录、不生成文件。

若使用文件方式，应将文件放在发布目录之外，运行账号可读，避免发布新版时被覆盖或删除；文件中只保存一行完整 Base64 字符串。同一套服务的多个实例必须使用同一份密钥。

首次准备密钥时，可以在自己电脑的 PowerShell 执行以下代码，复制完整输出到受保护的配置或文件中。这是一次性准备操作，不要放进每次启动脚本：

```powershell
$bytes = New-Object byte[] 64
$rng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
try {
    $rng.GetBytes($bytes)
    [Convert]::ToBase64String($bytes)
} finally {
    $rng.Dispose()
}
```

已有环境的手工配置示例：

```yaml
security:
  jwt:
    secret: "替换为自己生成的完整Base64字符串"
```

`local` 自动生成与显式配置都要求至少 64 字节原始密钥内容。生产环境缺少配置、密钥过短、Base64 格式错误、文件损坏或无法读写时，后端会拒绝启动并给出说明，不会静默换钥。

## 文件丢失或损坏

先检查日志中的路径和运行账号权限，优先恢复原文件备份。损坏的现有文件不会被自动覆盖。若原文件已经丢失且决定重新生成，本地模式在文件不存在时会生成新密钥，旧登录凭据随之失效，需要用户重新登录；业务数据库记录不会因此被删除。
