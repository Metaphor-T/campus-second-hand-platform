## 当前结论

首次验收的 5 项缺陷已修复。本轮结果：**后端 123 项通过、前端 12 项通过、前端构建通过、真实接口及浏览器验收 53 项全部通过**。

新增库存记录字段的迁移 SQL 已在独立测试库执行，并重复执行一次确认可重复使用。稳定项目与 `project_db` 未修改，未推送 GitHub。

**稳定部署前仍须核对历史订单的实际库存扣减记录。** 系统过去没有保存这项事实，无法仅凭现在的商品库存可靠还原。迁移脚本不会猜测；库存事实缺失的历史订单取消/同意退款会返回 409，并保持订单和库存不变。其他查询、支付、发货等仍按权限和状态规则处理。此保护不是历史记录已核对完成的证明。

## 五项修改

| 原问题 | 修复方式 | 复验结果 |
|---|---|---|
| 第三方用户可查看订单详情 | 在服务层校验当前用户为买家或卖家；返回真正 HTTP 403 | 买家/卖家允许，第三方/未登录拒绝 |
| 库存 3 买 2 提前下架 | 修正 MySQL UPDATE 中扣减后的库存判断，不再二次减数量 | 剩余 1 保持可购买；售罄才下架 |
| 不限库存取消订单变有限库存 | 持久化订单实际扣减数量；0 表示未扣减，只返还实际扣减数量 | 不限库存取消及退款后仍为 0 |
| 页面每页 100 条与接口限制不一致 | 前后端统一支持最大 100，101 及以上拒绝 | 100 成功、101 拒绝 |
| 重复审核返回 HTTP 500 | 正常业务冲突改为 409；非法审核参数 400；审核增加状态/版本条件与版本递增 | 重复审核拒绝；并发审核仅一方成功 |

同一订单的状态变更在事务中通过 `SELECT ... FOR UPDATE` 串行处理，避免重复取消、卖家和管理员同时退款时重复返还库存。订单业务错误使用明确 HTTP 状态，未预期异常仍为 500。

## 数据库迁移与历史订单

迁移文件：[20261109_order_stock_deducted_quantity.sql](../sql/migrations/20261109_order_stock_deducted_quantity.sql)。只对 `order` 增加 `stock_deducted_quantity` 可空非负整数字段：

- 新订单：有限库存填写实际扣减数量；不限库存填写 0。
- 取消/退款成功后清为 0，防止二次返还。
- 迁移前已取消订单：安全填为 0，因为不会再次返还。
- 其余历史订单：保留 NULL，脚本输出待核对编号，不根据当前商品库存自动回填。

已在 MySQL 8.0.45 的 `campus_system_dev_test` 验证添加及重复执行，旧表记录未整库替换。脚本使用 MySQL 5.7/8.0 通用语法，但本轮未实际运行 MySQL 5.7。

测试库执行前备份：`.local-backups/before-player2-fixes.sql`。仅含本机数据，Git 忽略，不同步稳定项目。

未来获准同步时的顺序：备份稳定库和代码 → 停止稳定后端 → 在明确选定的稳定库执行迁移 → 依据可信历史记录逐单核对 NULL 记录，未扣减填 0、已扣减填实际数量 → 同步完整相关代码并启动 → 复核查询、取消与退款。此流程尚未在稳定项目执行。

如果历史记录不能证明确切扣减情况，应保留待核对状态，由业务人员确认；不要用测试库覆盖原数据库，也不要直接把全部 NULL 填成 quantity 或 0。
